# Purchase Order Module

GD1 `purchase_order` converts approved PR lines into supplier commitments and carries the lifecycle from draft order through supplier confirmation, shipment, receipt, and closure.

```text
purchase_request_line -> purchase_order_line -> purchase_order -> shipment_line
```

## Scope

In scope:

- Create PO from one or more approved PR lines.
- Split one PR line across multiple supplier POs.
- Validate remaining PR-line quantity before conversion.
- Track PO type: `SEA`, `AIR`, or `DOMESTIC`.
- Track supplier confirmation, ETA/ETD, tolerances, revision, and landed-cost allocation on PO lines.
- Generate PO-stage tasks from active templates when the PO enters operational stages.
- Emit ERP sync/outbox events when supplier confirmation or revision requires integration.

Out of scope for GD1:

- Full supplier portal.
- GRN warehouse operation and stock posting, which belongs to future GD2/WMS.

## Tables

| Table | Purpose |
|---|---|
| `purchase_order` | Supplier order header: PO number, supplier, PO type, status, revision, terms, ETA/ETD, tolerances. |
| `purchase_order_line` | Ordered quantity sourced from a PR line, shipped/received rollups, unit price, landed-cost allocation. |
| `po_stage_task` | Runtime checklist/work items generated by PO stage. |
| `po_task_template` | Config used to generate PO-stage tasks. |

## Status

```text
DRAFT -> SENT -> CONFIRMED -> IN_PRODUCTION -> READY_TO_SHIP -> SHIPPED -> RECEIVED -> CLOSED
CANCELLED
```

Runtime compatibility note: code may still expose older status values while the GD1 migration is incomplete. New docs and validations should use the GD1 status set above.

## Rules

- A PO line must have `qty_ordered > 0`.
- If linked to a PR line, total converted quantity must not exceed `qty_requested`.
- Editing a PO after `SENT` should create `revision + 1` and require supplier reconfirmation.
- `CONFIRMED` and later states require supplier confirmation metadata.
- Shipment line quantity cannot exceed PO-line ordered quantity plus tolerance.
- `qty_shipped`, `qty_received`, and `landed_cost_alloc` are backend-owned derived fields.

## API Notes

Core actions:

- create PO from PR lines
- list/detail PO
- advance PO stage
- sync/queue ERP event
- revise PO after supplier send/confirm
- list/update PO-stage tasks

Backend routes currently live under `server/modules/purchaseOrders`, with shared logic in `server/services/logisticsPurchaseOrders.ts`, `server/services/poStageTasks.ts`, and `server/services/reliability.ts`.
